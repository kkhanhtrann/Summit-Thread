# Architecture and handoff

Two TypeScript applications target Node 24. Express composes the backend modular monolith; Vite/React renders the browser. PostgreSQL/Prisma owns durable state. Elasticsearch is backend-owned, rebuildable retrieval infrastructure. Keep credentials and AI provider SDKs on the backend.

## Ownership

`backend/src/app.ts` composes HTTP middleware and routes. `server.ts` wires clients and manages lifecycle; telemetry initializes through the Node preload before instrumented imports. Feature HTTP validates and delegates; application services depend on explicit ports, not Express. Persistence implements its owning feature's ports. Shared clients/configuration/instrumentation belong outside application services. Cross-feature imports use `public.ts`. Add feature modules when behavior exists; do not add dummy implementations.

The integration owner coordinates schema changes, app composition, OpenAPI and generated output. Each feature owner delivers its backend and web behavior vertically. Browser API/state adapters use `web/src/lib/api/http.ts`; pages own presentation. Static tests enforce browser provider/storage exclusion, application/Express separation, and feature entry points.

## Shared schema and contracts

`backend/prisma/schema.prisma` establishes rooms, released-caption sequences, revisions, source/playback state, topic threads/occurrences, selected visual metadata, and indexing jobs. ST-02 implements room and uploaded-source endpoints against this schema. Caption writes, release cursor/revision updates, and indexing jobs commit atomically under a room lock. Elasticsearch can be rebuilt from committed records and cannot release content.

`backend/src/features/sessions/contracts/session.contract.ts` defines initial room creation/snapshot, captions, topic evidence, source/playback/upload/window status and revisioned event shapes. `private-chat/contracts/privateChat.contract.ts` establishes private question/history/citation shapes; `search/contracts/captionSearch.ts` is the released-caption retrieval port. These are handoff contracts; coordinate limits and additions with feature owners. Backend OpenAPI describes health, room snapshots/events, source upload, shared playback, media delivery, and the visual-moment image and live-clip routes (see the [visual moments guide](features/visual-moments.md)). Extend it and regenerate `web/src/lib/api/generated.ts` when a feature adds working HTTP behavior. The [rooms and playback guide](features/rooms-and-playback.md) documents WebSocket validation, source clocks, capture cancellation, and finalization/flush ordering.

Room codes are eight characters; source timestamps and room-scoped stable identifiers govern evidence. Interim speech and unreleased analysis remain outside durable attendee state. SSE revisions must support snapshot refresh after gaps and reconcile concurrent events. Playback, continuous transcription, topic work and selected-frame work run independently. No attendee workflow waits for full media analysis.

ST-02 owns rooms/media/transcription; ST-03 owns thread identities, evidence and catch-up; ST-04 owns elapsed video windows and released original stills; ST-05 owns durable retrieval and private cited answers. Agree interface extensions before changing shared contracts. ST-06 integrates the resulting workflows and evidence. Deployment, login, TURN and Kubernetes are outside this local foundation.

`RoomService` owns fresh rooms and committed speech publication; `RecordingService` owns source validation and shared playback through explicit persistence and asset ports. `PrismaRoomRepository` stores room/source mutations and caption/index-job transactions. The transcription coordinator owns transient provider capture generations and serialized final writes; the HTTP gateway owns origin, message, PCM and source-clock validation. Platform media and Gemini adapters supply external resources. The web keeps join, presenter, attendee reading, feed reconciliation and source-audio capture in their owning vertical slices; shared transport owns HTTP/upload/SSE requests. `TopicAnalysisWorker` owns topic scheduling, backoff and skips through `PrismaSessionRepository`, which commits each validated plan under the room lock; snapshots load released captions, threads and occurrences through the shared `loadSnapshot` transaction reader. The [topic threads guide](features/topic-threads.md) documents cadence, evidence and recovery.
